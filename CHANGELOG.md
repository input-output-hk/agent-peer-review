# Changelog

Notable changes to `@input-output-hk/agent-review` and `@input-output-hk/agent-review-pi`. The two packages are versioned in lockstep.

## Unreleased

### Upgrading from 0.5.0, in one paragraph
- **This release merges pull requests 0.5.0 refused.** Three of the fixes below remove deadlocks in the safety gate rather than loosen it, and the visible effect on a repository already running `autonomy: "auto"` is that changes which sat at `proposed` forever now reach `auto` and merge. The largest single cause is rail 7: any human review of any kind used to fail it, so on every repository where a human ever reviews, the auto path was unreachable, and the pull requests that piled up were the ones a person had already approved. Rails 4 and 5 were unsatisfiable in the same way for the operation whose own approval was the missing requirement. If you have `auto` enabled anywhere, read the two sections below before upgrading, and consider running the affected flows in `propose` for one sweep to see what the gate would now do. Propose is still the default everywhere, and nothing in a configuration file can turn it up.

### Security invariants and least-privilege behavior
- `botAllowlist` is tighten-only. A pi tool call could previously replace the default dependency-bot allowlist, letting the same model invocation that requested `autonomy: "auto"` trust an arbitrary Bot account. That was especially dangerous because the dependency policy does not inspect lockfile content. Explicit lists are now intersected with `DEFAULT_BOT_ALLOWLIST` in both the steward and peer-request operations; extra identities are ignored.
- Claim-marker cleanup authenticates the marker's asserted reviewer against the GitHub comment author before deleting. A forged marker could previously make `claim`, `complete`, or `enrich` delete a maintainer's comment when the token had permission to do so. Marker authorship remains advisory for panel role assignment under the trusted-internal posture, but attacker-controlled text is no longer authority for a destructive operation.
- Least-privilege expedition calls fail closed without crashing. A 403 reading checks or commit statuses becomes an unconditionally failing sentinel, even when branch protection names a required subset; a 403 updating a behind branch becomes a visible `blocked` result. `init` now preflights Checks read, Commit statuses read, Administration read, and Dependabot alerts read, while `SECURITY.md` distinguishes the reads needed in propose mode from Contents write needed for an auto merge.
- Hostnames are private by default. Claim markers written with `captureMetadata: false` no longer include the reviewing machine in either visible prose or hidden JSON; old markers still parse, and enabling capture still records the hostname as documented. The dashboard accepts these machine-less markers and migrates existing databases to a nullable claim machine without losing rows. Its footerless second-opinion parser also bounds the verdict label to 200 single-line characters, removing a quadratic scan over attacker-controlled review bodies.
- Octokit's production throttling and retry plugins no longer run over the injected in-memory test transport. Endpoint mapping, error propagation, pagination, and conditional caching are still exercised, while the suite no longer spends nearly 30 seconds in artificial rate-limit spacing or risks a five-second timeout during retry backoff. The real network client keeps both plugins and their bounded retry policy.
- The test gateway now defaults the security-alert read to unreadable rather than zero and emits real chronological ISO review timestamps beyond id 9, preventing fixtures from accidentally passing a safety rail or inverting the latest verdict. Root `npm run test:all` now runs the core, pi, and dashboard suites together.
- The Pi Package bounds both host peer ranges below 1.0.0. A future major of the type-only `pi-coding-agent` peer can no longer satisfy the package silently even though its TypeBox tool schemas govern the expedition parameter clamps, and the optional `pi-taskflow` engine is bounded the same way.
- Lockfile recognition now comes from one exported basename allowlist shared by the path classifier and the dependency-upgrade classifier. Adding a lockfile on only the steward side could otherwise synthesize an auto-eligible dependency result for a path the general classifier did not recognize.
- `pr_watch.maxReviewRounds` is tighten-only in both its TypeBox schema and its runtime adapter clamp. A caller can hand a pull request to a human before the built-in three-verdict limit, but cannot pass `999` to disable that safety handoff.

### Approval semantics: a finished human approval no longer blocks, and a stale approval no longer authorizes
- A dismissed peer verdict is now a visible `hold-for-human`, not a silent `none` reported as "comments but no verdict." `watchAndReReview`, branch-protection approval counting, and dependency-steward idempotency now share one exported verdict-state definition and one latest-verdict map, including `DISMISSED`. This preserves `headMoved` when GitHub dismisses a stale review after a push and prevents an older dismissed or approved row from overriding a newer standing verdict. Addresses [#71](https://github.com/input-output-hk/agent-peer-review/issues/71).
- Rail 7 asked one question that was really two, and got both wrong. A single boolean, `humanReviewInFlight`, was true as soon as any human had left any review in any state, and a GitHub review is permanent history, so it could never become false again. On a repository that requires an approving review, the review that satisfied rail 5 was the same event that failed rail 7. The question is now split into the two facts it was conflating, each with its own reason string so a proposal comment explains itself accurately: a human with an **open review request** has been asked and has not answered, which is the only state anything can be raced and fails as `a human review is in flight`; and a human whose **standing verdict is `CHANGES_REQUESTED`** has finished and said no, which fails as `a human has requested changes` until they replace that verdict with another one. A human's standing `APPROVED` no longer blocks anything: it is the outcome the workflow wants, and it already counts toward rail 5. A `COMMENTED` review never blocks, whoever left it and whenever, because a comment states no position, which is already this package's rule everywhere else. `GateInput` now takes `humanReviewPending` and `humanChangesRequested` in place of the old single field, and `humanReviewStatus` in `core/expedition/human-review.ts` is what answers both. An unlisted login is still assumed to be a human; that part was never the bug. Addresses [#57](https://github.com/input-output-hk/agent-peer-review/issues/57).
- Rail 5 now counts an approval only at the commit being evaluated. `countApprovalsByOthers` ignored `commitId`, so a peer could approve `sha0001`, the author could push `sha0009`, and the gate would merge `sha0009` on the strength of an approval of code nobody had seen. The one exception is a branch with `dismiss_stale_reviews` enabled, where GitHub retires approvals on every push and has therefore already answered the question; that flag is new on `BranchProtectionSummary`, read from `required_pull_request_reviews.dismiss_stale_reviews`, and mirrored in the test gateway. Refusals are scoped the other way on purpose: an approval of an old commit does not **count**, while a `CHANGES_REQUESTED` on an old commit still **blocks**, because each rule fails toward not acting. `hasStandingApproval` applies the same scope as the count, so an operation holding a stale approval of its own does not withhold the pending approval that rail 5 needs. Both questions are answered from one implementation of "which of a login's reviews is the live one" (`standingVerdicts`, exported from `core/expedition/protection.ts`), so rails 5 and 7 cannot disagree. Addresses [#53](https://github.com/input-output-hk/agent-peer-review/issues/53).
- `watchAndReReview` asks the same "is a human involved" question and now answers it from the same place, so a drive-by comment or a passing maintainer's approval no longer freezes the reviewer on that pull request for good. Its result also carries a new `headMoved` boolean, so a flow can see that a standing verdict was left on a commit that is no longer the head without parsing prose. It matters most on `approved`, where it says the approval is stale and rail 5 will not count it. Nothing acts on it yet; a re-affirmation round is the follow-up.

### Flows: every gate refusal now reaches a person, and no state strands a pull request silently
- The requester escalates on the refusal, not on the rail. `pr-requester`'s step 3 used to request a peer review only when a gate reason began with `not auto-eligible:` and named source or test paths, and rail 1 is the only rail that produces that prefix. A refusal from branch protection, the size cap, the security-alert rail, or the human-review rail therefore ended the item with no merge, no reviewer, and no attention line, reporting `proposed=1 review-requested=0` and nothing else, forever. Step 3 now runs whenever the gate refused and asks unconditionally: no reason text is matched anywhere, because `pr_request_review` is idempotent and is what decides whether anybody is already engaged. Rail 1 stays in the prose as the clearest case rather than as the condition.
- All three summarizers gained an attention line for each state that strands a pull request: a gate refusal with nobody asked, quoting the first reason; a missing reviewer configuration; `expedite: "not-eligible"`, where the gate never ran; and a refusal held by a review the gate reads as a human's. That last one is broken out as its own `human-review-hold` count in every flow, because it is the one refusal an operator can cause by configuration alone, and "the gate is waiting for a human" and "the gate is waiting forever" are indistinguishable in any other number. In `pr-reviewer` it separates a hold for a review in flight from a spent round cap, which read identically before. A wrong `knownAgentLogins` is now a number and a line instead of silence.
- A missing `reviewers` configuration is loud. `pr_request_review` throws before its first GitHub call, so nothing is written anywhere and the pull request carries no trace of the attempt. The requester now reports `requested: "unconfigured"` rather than a silent `skipped`, and the summary names both the config field and the environment variable to set. Addresses the highest-priority half of [#51](https://github.com/input-output-hk/agent-peer-review/issues/51).

### Idempotency: a review round per head, a claim that re-pins, and a cap spent only on verdicts
- A peer review request is keyed on the head commit. `already-requested` held only while an OPEN request stood, and submitting a review clears that request natively, so the tick after the peer answered asked again, at an unchanged head, forever. `requestPeerReview` now answers `already-requested` when the trigger label is present and a target reviewer has either an open request or a review at the current head. Any review state at the head counts, `COMMENTED` included, because the question is whether this exact diff has been looked at. Reviewer logins are compared case-folded, since a case mismatch there would restore the loop.
- `claimReview` re-pins a stale claim marker. It used to resume whatever commit an existing marker named, and nothing ever moved it, so a stalled agent re-claimed a dead commit indefinitely, reviewed code that no longer existed, and the drift that produced read to `pr_watch` as an author push, manufacturing another round with no author action. The claim is now re-pinned to the current head as a delete followed by a post, in that order, because posting first and failing to delete would leave two markers and re-pin once per tick forever. The marker format is untouched, so every marker in the wild parses exactly as before and the parse stays a single linear pass. Only the SHA changes: `claimedAt` is carried over, so a re-pin cannot reorder the panel and an anchor stays the anchor.
- The review round cap counts verdicts, not reviews. `watchAndReReview` counted every review by the acting login, and a `COMMENTED` review asks the author for nothing: a second opinion is one, and so is a primary that `completeReview` downgraded because a competing one existed. Two of those plus one real verdict exhausted a cap meant for three rounds, and since the count only grows, `hold-for-human` was then permanent. Addresses [#52](https://github.com/input-output-hk/agent-peer-review/issues/52).

### Bot identity: one bot under two names is now one bot
- A bot reaches this package under two names. The pulls API reports the REST login `renovate[bot]`; GraphQL, the `gh` CLI, and therefore `pr-steward/discover.mjs` report `app/renovate` for the same App. The allowlist was compared as an exact string, so the steward answered `not-eligible` on every tick, wrote nothing, and the summarizer gave it no attention line. A new `normalizeBotAuthor` folds `app/x`, `x[bot]`, and case to one identity, and it is the single definition every other question is answered from: `isAllowlistedDependencyBot` folds both sides of its comparison, so one entry covers both surfaces; `looksLikeBotAuthor` is derived from the fold rather than restated, which is what keeps the two from drifting again; and `confirmsBotAuthor` is the shared "is this really a bot" rule that `approveDependencyUpgrade` and `requestPeerReview` both use, so the two cannot disagree about who owns a pull request. GitHub's answer wins wherever it has one, so an allowlisted name GitHub reports as a `User` is still refused in both operations. A name that is nothing but an affix is deliberately not folded, so two of them cannot compare equal. The `pr-steward` flow's default `botAuthors` list gained `app/renovate` alongside `app/dependabot`, so the bots the tool accepts are the bots the flow discovers. Addresses [#50](https://github.com/input-output-hk/agent-peer-review/issues/50).

### Setup, defaults, and dead configuration
- `runChecks` is gone from `ConfigSchema` and from the documentation. No non-test code path ever read it, so it was removed rather than wired up. The two places that mattered were the skill files, which told the reviewing agent not to run the repository's build or test scripts *"unless `runChecks` is enabled"*, reading as though there were a way to enable it. There is not, and there should not be: the diff under review is untrusted input, so executing it is out of scope for a review. The rule is now unconditional, which is both accurate and stronger than what it replaced. ADR 0007 keeps its original decision text and carries a dated note recording the change. Addresses item 5 of [#55](https://github.com/input-output-hk/agent-peer-review/issues/55).
- `agent-review init` gained `--known-agent-login <login...>` (repeatable), mirroring `--reviewer`. It writes `knownAgentLogins`, and the printed summary names the resulting list, because three separate documents already call that field the easy one to forget and its failure mode is silence rather than an error.
- The expedition auto-merge tools resolve a merge method instead of always trying `merge` and taking a 405 on a squash-only or rebase-only repository. An explicit per-call `mergeMethod` still wins outright, then a new per-repository `mergeMethodByRepo` config entry (`owner/name` to `merge`, `squash`, or `rebase`), then a best-effort read of the repository's own allowed methods through a new optional `GitHubGateway.getAllowedMergeMethods`. The probe runs only when autonomy is `auto`, so the propose-only path costs no extra API call, and a gateway that does not implement the optional member is treated as "cannot tell" rather than "everything is allowed".
- All three `discover.mjs` scripts warn on stderr when a `gh` call returns exactly the `--limit 100` cap. `gh` truncates silently past that with no other signal, so a sweep over a busy repository could quietly skip work.
- The pi extension memoizes its default gateway per process, built at most once and lazily on first use, instead of constructing a fresh client with a cold ETag cache and no cached authenticated login on every single tool call. An injected gateway is unaffected.
- `SECURITY.md` and the quick start now name the permission the security-alert rail needs beyond the base recommended scope, **Dependabot alerts: read** for a fine-grained token or `security_events` for a classic one, and `init` makes one best-effort read-only probe of that endpoint and prints an unmissable warning when it cannot read it. Without that permission the read 403s, the count is unreadable, and rail 6 fails closed on every pull request, which makes `autonomy: "auto"` inert. The rail's own scoping (repository-wide rather than scoped to the change) is still open as [#54](https://github.com/input-output-hk/agent-peer-review/issues/54).

### Documentation
- `docs/how-it-works.md` is a new page: every flow, operation, and safety rail as a state machine, with a table beside each diagram carrying the detail a diagram cannot. It is drawn from the code rather than from the design's intentions, and `test/taskflows.test.ts` now holds it to that with a status-vocabulary contract: for each operation, the statuses named in the page's side-by-side table must equal the operation's own TypeScript union, in both directions, so a renamed, added, or removed status fails CI instead of aging quietly in prose.
- Every shipped skill's frontmatter is parsed by a test, `docs/taskflows.md` documents the per-repository setup a flow needs before its first run, and `AGENTS.md` covers the three flows for an agent installing this package on someone's behalf.
- Taskflow installation now says explicitly to copy the two sibling definition files plus the four-file directory for each flow. It points at the package templates rather than the repository's dogfood configs, which intentionally target this repository. Copying only the directory, as the old instructions said, left the flow unresolvable. Addresses the documentation half of [#68](https://github.com/input-output-hk/agent-peer-review/issues/68).

### pi package
- Fixed the `agent-review` skill's frontmatter so pi loads it at startup again. The long `description` value was an unquoted YAML scalar containing `": "` sequences (for example `Drives the full loop: list open requests`), which every YAML parser reads as a nested mapping inside a plain one; pi failed with `Nested mappings are not allowed in compact mappings at line 2, column 14`. The value is now double-quoted; its text is unchanged.

### Steward role: an agent can now approve a bot dependency pull request it is qualified to approve
- Gate rails 5 and 4 no longer block the operation that supplies the approval. On a repository that requires an approving review the missing review failed both of them, for the same one reason: rail 5 compares the standing approvals against the required count, and GitHub's own `mergeStateStatus` reads `blocked` for exactly as long as a required review is outstanding, which failed rail 4. `protectionSatisfied` gained `pendingApprovalFromActor`, `GateInput` gained the same field for rail 4, and `gatherRails` gained `willApproveAs`, which grants the allowance only when the acting login is not the pull request's author and holds no standing approval (new `hasStandingApproval` keeps that judgement identical to `countApprovalsByOthers`, so one approval is never counted twice). Before this, the auto path was unreachable for `approveDependencyUpgrade` on exactly the repositories it is for, whose own approval was the missing requirement. Neither allowance is a bypass: rail 5 adds exactly one, so two required approvals with none present still holds the change back; rail 4 tolerates `blocked` alone and still refuses `dirty`, `unstable`, `behind`, and `unknown`, because approving would not change any of those; unreadable protection and required conversation resolution still fail closed; required checks must still be green; and a malformed count is still rejected before the increment applies. `expedite` merges rather than approves, passes no `willApproveAs`, and is unchanged on both rails.
- `approveDependencyUpgrade` re-reads every rail **after** approving and runs the whole gate a second time without either allowance, merging only if the second evaluation still returns `auto`. So a pull request GitHub still reports as `blocked` once the approval is in does not merge: it reports `approved`, and a later tick merges it once GitHub has recomputed the state. Re-running the gate rather than re-reading a chosen few rails is the point: approving is a write, and a human review, a red check, a new security alert, or a moved head arriving in that window each stop the merge, as does protection the approval turned out not to satisfy. A new `approved` result reports the approval landing without the merge, naming the rail that refused, since an approval is durable and unblocks the pull request for whoever merges it next. The approving review body now carries the verdict rather than a bare event: change class, semver level, the changed packages with old and new versions, the size, the head commit, and which rails passed. A review of this agent's own that a maintainer has DISMISSED at the current commit is a hard stop: re-approving would override an explicit human refusal that no other rail can see.
- A dependency-specific size policy, `DEPS_GATE_POLICY` (10 files, 4000 lines), is what `approveDependencyUpgrade` defaults to, per field and still overridable. What the larger cap rests on, stated plainly: manifest lines are read and verified to be nothing but paired dependency version edits, lockfile content is not read at all, and those lines are trusted on the authorship rail instead (an allowlisted dependency bot GitHub confirms is a Bot, regenerating a lockfile from the verified manifest edit). At the old 200-line cap a full lockfile regeneration went to a human and at 4000 it does not; a line count was never evidence about lockfile content either way. The file-count cap and every other rail are unchanged. `pr_approve_dep_upgrade` now exposes `maxFiles` and `maxLines`, clamped to that policy the same tighten-only way `pr_expedite` clamps to `DEFAULT_GATE_POLICY`.
- `requestPeerReview` refuses a pull request authored by one of the dependency bots the steward path accepts (`DEFAULT_BOT_ALLOWLIST`, which a caller may only tighten) with a new `bot-authored` status, and writes nothing at all, no label and no request. GitHub only forbids approving your own pull request, so an agent may review and approve such a change itself, and handing a machine-checkable dependency bump to another engineer's agent adds a round trip and a person's queue for no gain. Membership uses the same comparison the steward uses, so a pull request cannot be refused by one and declined by the other; confirmation that a listed name really is a bot comes from GitHub's actor type or the name shapes a bot carries (`name[bot]`, `app/name`), and an unreadable actor type is treated as "not a bot" rather than failing the call. Any other bot is still requestable, which matters: a codegen or release bot's source changes are exactly what a peer review is for. `pr_request_review` surfaces the status, and the `pr-requester` flow reports it and stops. The `pr-steward` flow's default `botAuthors` list gained `app/renovate` alongside `app/dependabot`, so the bots the tool accepts are the bots the flow discovers.
- The test gateway's unseeded mergeable state is now `unknown` (a state that fails the gate) rather than `clean`. That one default let tests seed branch protection requiring an approving review and still be handed a clean mergeable state, a combination GitHub cannot produce, which is how the rail 4 deadlock survived two review passes: the tests asserted an impossible world and passed. A test that cares about the mergeable state now has to say which one it means, and a merged pull request stops reporting `clean` even when `clean` was seeded.
- All of it stays **propose-only by default**: none of these paths is reachable without an explicit `autonomy: "auto"` on that individual call, and no configuration file can supply it. Addresses [#48](https://github.com/input-output-hk/agent-peer-review/issues/48) and items 1 and 2 of [#39](https://github.com/input-output-hk/agent-peer-review/issues/39).

### Setup: `init` now produces a config that works, and a mistyped config key is no longer discarded
- `agent-review init --repo owner/name --yes` wrote `{}`, so the very next command answered `--repo is required (or set defaultRepo in your config)` after a setup that reported complete success. It now records the `githubLogin` it had already resolved, and sets `defaultRepo` when exactly one `--repo` was given. Exactly one, because with several passed there is no basis to elect one, and an existing `defaultRepo` still wins, so a hand-set default survives a re-run.
- Interactive `init` asks for `reviewers` and `knownAgentLogins`, and the printed summary names `defaultRepo`, `reviewers`, and `knownAgentLogins` whether they are set or not. Both fields were flag-only, so the interactive path could finish reporting success and still leave the tool unable to request a review (`No reviewers: pass --reviewers`) or unable to tell a peer agent from a human on the expedition gate. Pressing enter at either prompt leaves whatever an earlier run recorded alone rather than clearing it.
- **The config schema is strict.** An unknown key used to be stripped silently, so a config of `{"knownAgentLogin": ["peer-bot"]}` loaded as all defaults with exit 0 and no warning, and the field whose failure is quietest, `knownAgentLogins`, was the one most exposed. `schemas/config.schema.json` has always published `additionalProperties: false`; the runtime now agrees with it. The error names the file, each unknown key, and the field it was probably meant to be (`knownAgentLogin` -> `knownAgentLogins`, `reviewer` -> `reviewers`), and explains a field an older version wrote, such as `runChecks`, rather than guessing at a near miss. If a config file has such a key, this is a breaking change: fix or delete the key.
- A failed label bootstrap says what to do about it. `init` writes the config file before bootstrapping, so a token without Issues write on the repository failed with a bare `Resource not accessible by integration`, naming no repository, no permission, and giving no hint that a usable config was already on disk. All three are now named, a 404 is reported as a repository that was not found rather than a permission to grant, and the CLI's auth handling matches 403 and 404 alongside 401.
- Octokit's own request log no longer leaks into CLI output: `GET /user - 401 with id ... in 570ms` printed above the friendly message and read like a crash. Only the per-request narration is silenced; the error itself still propagates, and GitHub's deprecation and rate-limit warnings still reach the console.
- `bootstrap` lists a repository's labels once for the whole profile instead of once per label, so the first command a new user runs makes one round trip there rather than twelve. `ensureLabel` takes the snapshot as an optional argument and still lists for itself when called standalone.
- The pi package gained a `prepack` script, so a hand-run `npm publish` cannot ship a tarball with no `dist/` while `pi.extensions` points into it. Addresses [#67](https://github.com/input-output-hk/agent-peer-review/issues/67).

## 0.5.0

### Expedition taskflows
- Five new core operations, exported from `@input-output-hk/agent-review`, that act on a pull request instead of reviewing one: `stabilize` (sync a branch with its base, reporting `up-to-date`, `updated`, `conflict`, `blocked`, `draft`, or `gone`), `expedite`, `requestPeerReview`, `approveDependencyUpgrade`, and `watchAndReReview`. With them: the central safety gate (`evaluateGates`, `DEFAULT_GATE_POLICY`), the path-based change classifier (`classifyChange`), the dependency-upgrade classifier, and the action-marker helpers (`buildActionMarker`, `findActionMarkers`) that keep a proposal comment idempotent per head commit. The gateway grew the reads and writes these need: mergeability, check runs, branch protection, detailed pull files, requested reviewers, actor type, and the open security-alert count, plus `updateBranch`, `mergePull`, `removeLabel`, and `addAssignees`. Every one of them is propose-only unless the caller passes `autonomy: "auto"` on that individual call.
- Five new pi tools that move a pull request forward instead of reviewing one: `pr_stabilize` (sync a branch with its base), `pr_expedite` (evaluate the expedition gate, then propose or merge), `pr_request_review` (request an agent peer review, once per round), `pr_approve_dep_upgrade` (evaluate a bot dependency upgrade, then propose or approve and merge), and `pr_watch` (decide the reviewer's next action: `re-review`, `wait`, `hold-for-human`, `abandoned`, `approved`, or `none`). The two that can merge take an explicit `autonomy` parameter that defaults to `propose` and is never read from the config file, and their optional `maxFiles`/`maxLines` can only tighten the default size caps, never widen them.
- Three taskflows ship with the pi package under `taskflows/`: `pr-requester` (my own open pull requests), `pr-reviewer` (reviews requested from me, plus the pull requests I am watching), and `pr-steward` (bot dependency upgrades). Each one is a zero-token discover script, a bounded fan-out over the typed tools, and a zero-token summary. Copy a flow into a repository's `.pi/taskflows/`, list the repositories in its `config.json`, and run it with `/tf:<name>`. This repository dogfoods all three from its own `.pi/taskflows/`.
- Propose-only is the default everywhere and it lives in the flow argument, not in configuration: `autonomy` defaults to `propose`, and no config file the flows read can turn it up. Auto therefore takes a visible per-invocation opt-in (`/tf:pr-steward autonomy=auto`). Every flow bounds its fan-out at four concurrent pull requests.
- A `knownAgentLogins` array in the global config (`~/.agent-peer-review/config.json`), also settable with the comma-separated `AGENT_REVIEW_KNOWN_AGENTS` environment variable, names the logins that count as agents rather than humans when the safety gate asks whether a human review is in flight. Empty by default, which is the safe end: an unlisted reviewer is always assumed to be a human.
- `pi-taskflow` is an optional peer dependency of `@input-output-hk/agent-review-pi`, so it is not installed for you. The flows need it explicitly (`pi install npm:pi-taskflow`), and it requires Node.js 22.19.0 or newer. See `docs/taskflows.md`.

### Security and dependencies
- Cleared every fixable open Dependabot alert. `@fastify/static` moved to 10.1.3 and `vite` to 6.4.3 in the dashboard (which also clears `esbuild`), the docs site picked up patched `mermaid`, `js-yaml`, `nanoid`, and `dompurify`, and the `undici` transitives reached 8.9.0. The last one needed the `@earendil-works/pi-coding-agent` development dependency raised to 0.84.1: that package publishes its own `npm-shrinkwrap.json`, which pins its subtree and silently defeats a root `overrides` entry. Neither published package changed a runtime dependency, and the peer floor stayed at 0.83.0 so consumer compatibility is unchanged. Two `image-size` advisories in the documentation site's transitive tree remain open because no patched version exists upstream; they affect the docs build only, which reads this repository's own images.

### Release process
- On-demand releases from `main`. A one-click `Release` workflow (from the Actions tab) bumps the version across every workspace with a single semver-aware script, finalizes this changelog, commits to `main`, and creates the GitHub release, which the existing publish workflow ships. A new `check:version` CI gate keeps the version consistent across all files, and `npm run version:set <patch|minor|major>` performs the bump locally. See `docs/releasing.md`.

### Dashboard
- The local, unpublished `dashboard` package gained its full UI: the Overview, Repos, repo Pulls, and Pull detail views, a hand-rolled client router with a light and dark theme toggle, and sanitized rendering of review summaries and inline notes. Build it with `npm run -w dashboard build` and serve it with `agent-review-dashboard serve`.
- Two aggregate views and the endpoints behind them: **Agents** (one row per captured agent and model identity, with its review count, primary and second-opinion split, verdict distribution, agreement breakdown, average turnaround, and repository count, plus a single "Unknown" row for reviews with no captured metadata) and **Collaborators** (one row per pull request author, with the reviews and verdicts their pull requests received and how many distinct agent identities reviewed them). Both are filterable by repository, served read-only from `/api/agents` and `/api/collaborators`. Verdict counts exclude reviews that recorded no verdict, so the views show raw counts rather than shares of a total, and the agreement column states that it is derived from posted second opinions rather than an authenticated signal. Semantic `--success` and `--warning` theme tokens join `--danger` so a good, a bad, and an ordinary value never share the brand red.

## 0.2.0

First published release: an asynchronous AI-agent PR-review workflow over GitHub, usable from the CLI, an MCP server, and a pi.dev extension.

### Core workflow
- All state lives on the pull request: an `ai-review` trigger label, native requested-reviewers for routing, a claim-marker comment that pins the head commit SHA, and a native PR review as the completion signal. No external queue, database, or long-running server.
- A pure `core` library behind a `GitHubGateway` port, with thin CLI, MCP, and pi.dev adapters over one code path.
- Idempotent label bootstrap for the orthogonal label profile.

### Panel review
- Multiple requested reviewers run as a concurrent panel: the earliest to claim is the anchor and posts the single primary review; later claimants are enrichers that add one consolidated second opinion once the primary lands. Stale-anchor promotion cascades without deadlock, and a competing primary is guarded so exactly one primary is posted per round in normal operation.

### Review context
- On claim, the task carries auto-detected per-language checklists, deepened domain skills (security and OWASP, cryptography, architecture), and the reviewed repository's own agent context (`AGENT.md`, `CLAUDE.md`, `.claude`, `.codex`). All best-effort and bounded, and never able to fail a claim.

### pi.dev
- `@input-output-hk/agent-review-pi`: a native pi.dev extension registering the six review tools plus a skill, distributed as a Pi Package.

### Security
- Untrusted review context (the diff and the reviewed repo's own files) is fenced and labeled, with a served content policy that travels to every host. See `SECURITY.md` and ADR 0007.
- Linear claim-marker parsing (no polynomial backtracking) and a least-privilege CI token.

### Distribution
- Published to GitHub Packages. See the ADRs under `docs/adr/` for the load-bearing design decisions.
